Roadmap — trust-me-bro-ai

Deferred decisions & planned work, grouped by feature. When we hit something we're not building yet, we park it here and link the spot it touches — then revisit when we build that feature.

Stage 1 — get-requirement

Pull the requirement from an external MCP source Planned

Now
The requirement comes from the user's message or a local file (step 1).
Later
get-requirement can also pull the requirement from an external MCP server (e.g. an issue tracker or docs tool) — reading the ticket / doc as the requirement source, not only what the user pastes in.
Touches
get-requirement step 1 ("Read the requirement — user message / or file"). Extend the input source to include an MCP fetch.

Stage 4 — execute-tdd (TDD execution loop)

Multi-agent engineer dispatch Planned

Now
One-context — execute-tdd runs every task itself, regardless of effort.
Later
Route each task to an engineer agent by effort, and run independent tasks (no shared depends_on) in parallel.
Touches
execute-tdd dispatch step (step 3 — "read effort → choose engineer agent"). Modify around there.

Autonomous decision-making (fewer human gates) Planned

Now
Every blocking gap — deadlock, failure, an assume that doesn't hold — halts the loop and asks the human.
Later
A higher-capability model adjudicates routine decisions on its own; only genuinely important calls escalate to a human.
Why
With parallel / multi-agent execution the decision points multiply — gating every one on a human doesn't scale.
Touches
execute-tdd stop conditions (deadlock / failure / pre-flight assume check) and the per-task review gate.

Stage 6 — acceptance-review

AI self-review against Definition of Done (DoD) Planned

Now
Stage 6 opens straight at Summarize — no AI pass that checks the delivered work against a Definition of Done before handing it to the user.
Later
Before Summarize, the agent self-reviews the scenario against a DoD checklist (acceptance criteria met, tests green, E2E flow complete) and surfaces any gap first — so the human reviews work the agent has already vetted.
Touches
acceptance-review procedure — a new step 1 ahead of Summarize. DoD checklist content still to be defined.

New skill — update-library (dependency maintenance)

Standalone dependency / library update workflow Planned

Now
No skill for this — updating a project's dependencies is done by hand, outside the workflow, with no playbook or test-gated safety net.
Later
A standalone update-library skill: scan for outdated dependencies → bump versions → work through any breaking changes → re-run the project's tests to verify nothing regressed → report what changed. A maintenance workflow, separate from the 6-stage feature workflow.
Touches
New standalone skill (not a workflow stage). Reads tech-stack.md for the package manifest + test command; reuses the test/verify pass the way execute-tdd / api-test run and check tests.

create-skill — skill-eval fidelity levels

Graduated test levels for the after-edit run Planned

Now
The after-edit checklist runs a single vibe test — this same session is both actor and judge in the same session. Cheap on tokens and good at judging whether the skill is well-written, but the pass/fail itself is biased (it tends to pass regardless).
Later
Offer the run a choice of levels, each higher one trading more tokens for less bias / more real behaviour:
  1. Separate session — same model & reasoning, actor=judge, but a fresh session (drops the same-session bias).
  2. Different model — different model/reasoning, separate session, one skill at a time. Concerns: each needs its own harness wiring + a low/high boundary; and a skill that reads other reference files (e.g. "read template A, then create a file from it") gives skewed results when tested alone, because the ref files were never supplied.
  3. + ref files (1 depth) — supply the referenced files one level deep to fix level 2's blind spot; token cost jumps sharply.
  4. Mock-up / real repo — run the skill for real against a repo to check actual behaviour. Open question: how many tokens is enough? Not feasible yet (resources).
Touches
create-skill ## After You Create or Edit a Skill step 3 (Run and report) — currently fixed at the vibe level; this adds a level selector. Also the skill-eval/ harness for the separate-session / different-model / ref-file / real-repo runners.

Decision records (ADR)

Keep an ADR log of decisions already made Planned

Now
Decisions live as ad-hoc "Decision:" notes on the local design board (.tmp/design-skill.html, gitignored) — not committed, easy to lose, and hard to look up when a question turns out to have been settled already.
Later
Keep a committed ADR (Architecture Decision Record) log — one short entry per decision (context / decision / why / status) — so a settled question has a durable record instead of being re-litigated. Can supersede the board's scattered Decision notes.
Touches
New committed location; the board's existing Decision notes are the source to migrate. Format + where it lives still to be defined.
